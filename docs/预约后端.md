# 预约后端：主站 Spring Boot + MySQL

新版预约页面 `/page/booking` 和 `/api/booking` 使用主站相同的 Spring 会话、数据源和数据库事务。`booking/web/` 的 MRBS / PHP 源码保留作历史参考与迁移回退材料，主站模式不再调用它。

## 模块边界

Java 包：`com.qpwflshclub.formal_club.Booking`。

| 文件 | 职责 |
| --- | --- |
| `BookingPolicy` | 解释数据库规则；计算北京时间、下一周、开放日、完整时段和教师截止时间 |
| `BookingRepository` | 集中保存参数化 SQL、记录映射和数据库行锁 |
| `BookingService` | 提交事务、限额、冲突、幂等、队列分配与账号清理 |
| `BookingApiController` | 解析当前会话身份、校验写入令牌、输出当前用户可见数据 |
| `BookingWorker` | 每 30 秒处理到期教师队列，重启后自动补处理 |
| `frontend/booking.jsx` | 显示服务器提供的日期、时段与状态，提交预约、查看自己的记录 |

## 数据在哪里

全部使用主站 `spring.datasource`，没有第二个运行数据库连接：

- `club_booking_policy`：带版本的规则 JSON。字段对应 `BookingPolicy` 的明确类型；无效或重叠时段会被拒绝。
- `club_booking_court`：场地名称和启用状态。
- `club_booking_reservation`：正式预约、教师挂起与分配失败状态、备注、账号归属、幂等键、规则版本及旧记录编号。
- `club_booking_legacy`：原 MRBS 行的完整 JSON 存档，供迁移核对，仍在 SQL 中，不返回普通客户端。

时间区间存 Unix 秒，队列排序时间存 Unix 微秒，展示与规则统一用 `Asia/Shanghai`。数据库没有依赖浏览器时钟。历史预约即使不符合当前试运行时间，也保留原始时间和状态。

## 后端校验与并发

所有写入先在同一个数据库事务内锁定策略行，再检查重复提交、真实场地、须知版本、下一周日期、开放时段、20 分钟完整区间、学生开放窗口、日/周限额与冲突。各场地共用这一锁，防止同一账号通过同时提交不同场地绕过限额；不同 JVM 实例同样受 MySQL 行锁约束。

每周 3 次、每天 1 次同时计入正式预约和待分配教师请求。学生周六、周日 13:00–19:00 预约；教师请求按提交时间先后排队，前一周周日 19:00 后自动分配。学生在开放窗口的正式预约优先。重复提交相同幂等键只返回原记录，复用键改变内容会被拒绝。

教师队列由后台定时任务分配，不依赖打开页面。分配和账号注销也使用同一事务锁。注销在主站数据库事务中删除该账号预约和旧数据存档，不再向 PHP 发起远程删除请求。

## API

- `GET /api/booking`：账号展示信息、会话写入令牌、规则、场地、下周时段与占用状态。
- `GET /api/booking/mine`：仅当前账号的预约和排队历史。
- `POST /api/booking/reservations`：`courtId`、`start`、`end`、`note`、`rulesVersion`、`requestKey`；必须携带 `X-Workspace-Token`。

提交不接受用户身份或角色，身份取自主站会话。日历只显示占用与排队人数，不暴露他人邮箱、姓名或备注。客户端提交前的禁用按钮只改善体验，不能替代服务端校验。

## 配置和启动

先显式执行 `database/migrations/20260912-booking.sql`，导入场地和历史记录，再设置 `CLUB_BOOKING_BACKEND=main`。保留 `spring.jpa.hibernate.ddl-auto=none`。新安装无需旧数据时，应在 `club_booking_court` 中录入真实场地。

修改开放时间等规则时更新 `club_booking_policy.settings` 并增加 `revision`；须知发生变化时同时增加 JSON 内的 `rulesVersion`。前端展示从 API 读取。变更前检查待分配队列：不符合新规则的待分配请求会被标为未获分配，已确认的历史记录不会自动删除。

## 迁移与回退

工具位于 `deploy/export-bookings.py`、`migrate-bookings.py`、`cutover-booking.py`，依赖见 `deploy/requirements-booking.txt`。

1. 备份主站 JAR、环境配置、Nginx、私有目录和两套数据库。
2. 暂停旧站写入与教师队列定时器。门禁只影响预约，不影响其他主站功能。
3. 使用 UTF-8 导出原场地、预约、重复预约及教师队列。冻结后再导出最终快照，避免迁移期间漏单。
4. 在主站执行新增表迁移；先试导入（事务回滚），再正式导入。逐条验证归属、时间、状态、备注和原始字段，已确认的教师队列通过关联预约去重。
5. 切换主站服务，验证启动与数据后再开放预约。旧 `/booking/` 链接转到主站页面，旧表单写入拒绝执行；旧 PHP 服务和定时器保持停止，旧数据库保留。

导入是幂等的，但会拒绝覆盖变化过的源数据、冲突预约、缺失的队列关联和已存在原生预约的目标库。快照和 SQL 备份含个人数据，只放私有备份目录，不提交 Git。

开放新写入之前失败，可自动恢复旧服务；开放之后不能只回滚 JAR，否则可能丢失新预约。必须再次冻结写入，迁回新增记录并核对后再回退。不要同时启用两套预约写入端。

## 验证

`BookingMysqlTest` 使用真实 MySQL，覆盖并发冲突、跨场地限额、重复提交、时区边界、离线分配、重启恢复和注销清理。必须提供以 `_test` 结尾的独立数据库，测试会清理其中的预约表。

```sh
export BOOKING_TEST_URL='jdbc:mysql://127.0.0.1:3306/club_booking_test'
export BOOKING_TEST_USER='test_user'
# BOOKING_TEST_PASSWORD 从本机安全环境提供
./mvnw -Dtest=BookingMysqlTest,BookingAuthorizationTest,BookingControllerTest test
```

`tests/booking/test_migration.py` 在独立 MySQL 库验证试导入、重复导入、异常回滚和完整记录存档。未提供测试环境变量时，MySQL 集成测试会显式跳过，不代表验证成功。


## 本次回归

预约日历和规则由主库配置生成。浏览器只显示最后一次请求的结果，每格仅有一个预约按钮。真实 MySQL 测试覆盖抢占同一时段、跨场地每日上限、教师队列、重复请求、注销清理，以及旧数据完整归档和重复迁移。
